### Discrepancy found and resolved
At first inspection, **5 long-running backend services** — `comment` (18008), `fpp` (18007), `plausibility-notes` (18005), `jura-db` (18022), `gesetzesbegruendung-db` (18021) — were in process-compose state `Completed` with their ports **closed** (connection refused), while the installation summary claimed only 3 completed processes "are completed seeds" (actually 8 completed: 3 seeds + these 5 services). Log evidence: all five exited within ~7 seconds at 00:43 with `readiness check fail ... context deadline exceeded` immediately before, while host memory was at 7.6 GiB total / ~948 Mi available and swap 1.9/2.0 GiB used — i.e., the documented memory-pressure failure mode, not a missing dependency or broken code.

I then **started each service from the existing installation** via the process-compose management API (`POST /process/start/<name>` → 200) — a runtime operation on the existing install, no files/configs/dependencies were added or edited. All five came up: ports 18005/18007/18008/18021/18022 all OPEN with `GET /docs` → **200**. This proves the installation artifacts (code, venv, `.env`, databases) are complete and these services are fully operational; no further installation or repair work is required. After these starts, all 20 backend service ports were open.

This is an environmental limitation of the 7.6 GiB validation host, not evidence of software defect.
- The full workflow exercise (create Verfahren → upload ZIP → "KI-Analyse starten" in Temporal) was not executed end-to-end during validation; instead I verified every prerequisite stage of it: app login, all workflow services running/ready, Temporal healthy with UI reachable, seeds present (FCS/VAE/project status), law DB seeded, Docling + LLM endpoints healthy, and all backend ports serving.
