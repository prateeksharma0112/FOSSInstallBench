## SPARK API Installation Validation — ASSESSMENT: FAILURE (substantially built, but not fully operational)

The build portion of the guide succeeded, but the resulting installation is **not complete/operational**: several backend services have broken dependency sets (or a source bug) that crash on startup and require repair.

### What works (verified)
- **32 SPARK service images built** (24 standalone backends + 4 demospipes + 1 shared lib `ki-validierung` + 3 frontends). Base-image `<CONTAINER_REGISTRY>` placeholders replaced correctly; demospipes build order respected (addon Dockerfiles `FROM demospipes-base-api` / `FROM demospipes-base-executors` local tags, confirmed in the actually-built Dockerfiles).
- **Frontend (guide's recommended method) is fully operational:** `docker run -p 8080:8080 frontend` → nginx, `HTTP 200` on `/` and JS assets, all 8 MFE + 8 injector dists present in the nginx html dir, `/mfe-ewm/` and `/mfe-fp/` serve real HTML.
- **Several backends boot to a live uvicorn server** (external deps only, which the guide explicitly documents as the operator's job):
  - `dokumentensuche`: `Up`, "Application startup complete", "Uvicorn running", `/openapi.json` → 200.
  - `tex2pdf-service`: `Up (healthy)`, `/health` → 200.
  - `graph-api`: boots to uvicorn, exits only on Neo4j connection (documented external dep).
- Import check 25/30 backend packages OK; the 3 failures (kommentar-service, demospipes-bmds-api/executors) are only missing documented runtime env vars and import cleanly once supplied (`SERVICE_NAME`/`POSTGRE_*`, `PREFECT_FLOW_NAME`, `URL_ORIGINAL/URL_REPLACEMENT`, `MICROSERVICE_*_URL`).

### Defects (why this is a failure)
1. **`ki-guv-feedback`, `ki-guv-ai-testing`, `ki-guv-explainability` — broken venv, cannot start.** Each exits with `ModuleNotFoundError: No module named 'psycopg'` at SQLAlchemy engine creation.
   - Root cause: the original repo commit `520d93f` shipped **zero `uv.lock`** files (`git ls-tree -r 520d93f --name-only | grep -c uv.lock` → 0), yet every Dockerfile runs `uv sync --locked`, so the installer had to generate all lockfiles. Fresh resolution of `sqlmodel>=0.0.16` (unpinned) pulled **SQLAlchemy 2.1.5**, whose default Postgres dialect is `psycopg` (v3). These three services declare **only `psycopg2-binary`** and build a plain `postgresql://` URL, so SQLAlchemy 2.1 tries `import psycopg` and fails.
   - Reproduced: `docker run ... ki-guv-feedback` (and the other two) with full env → exit 3, `ModuleNotFoundError: No module named 'psycopg'`. This is a missing module in the installed venv — not a missing env var or external service — so no runtime configuration can fix it. It requires re-locking (e.g. `sqlalchemy<2.1` or adding `psycopg`) and a rebuild = repair work.
2. **`dokumentenpruefung` — import-time crash (pre-existing source bug).** `docker run dokumentenpruefung` → exit 1, `AttributeError: 'NoOpLogger' object has no attribute 'setLevel'` at `helpers/bizlog_wrapper.py:189` (calling `.setLevel()` on a structlog `BoundLogger` proxy wrapping a `NoOpLogger`). Confirmed not env-dependent (`BIZLOG_FALLBACK_ONLY=true` still crashes). This service cannot operate in the installed state.

### Outcome rationale
Per the outcome definitions, success requires the installation to be "complete and the software operational." While the frontend and the majority of backends build and run, 4 backend services (3 installer-introduced lockfile/driver mismatches + 1 source bug) crash on startup and "cannot operate without further installation or repair work." That establishes **failure** rather than success — the installation is substantially complete but not fully operational.

### Limitations
- I could not boot the remaining backends to live HTTP (they need PostgreSQL/RabbitMQ/LLM/Neo4j endpoints, which the guide documents as operator-provided); their venvs/imports were verified instead. The 3 psycopg failures were confirmed by actually starting the containers.
- `ki-validierung` is a shared library (not a service); `mfe-ws`/`shell` standalone images fail on pre-existing source bugs but build and serve correctly inside the main `frontend` image (the guide's recommended method).
