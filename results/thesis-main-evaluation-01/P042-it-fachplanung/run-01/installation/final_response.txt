Installation of IT-Fachplanung (tfm-fachplanung) completed successfully and was verified end-to-end.

**What was done**
1. **Prerequisite (ddev)**: The environment had Docker but no `ddev`. The official installer refuses to run as root, so DDEV v1.25.4 was installed manually by downloading the verified release tarball (`ddev_linux-amd64.v1.25.4.tar.gz`) from GitHub and placing `ddev`, `ddev-hostname`, and `mkcert` in `/usr/local/bin`.
2. **Non-root execution**: DDEV refuses to run as root. A non-root user `ddevuser` (uid 1000) was created, added to the `docker` group, and given ownership of `/workspace`; all ddev/composer/npm commands run as `ddevuser` via `su - ddevuser -c '...'`.
3. **Project start**: `ddev start` succeeded after fixing the LDAP container. The supplied `.ddev/docker-compose.ldap.yaml` bind-mounted `test_users.ldif` as a single read-only file, which caused the openldap bootstrap to fail (`chown ... Read-only file system`, then `sed: cannot rename ... Device or resource busy`, then `rm: cannot remove ... Device or resource busy`). I mounted the directory `.ddev/ldap-bootstrap/` instead and set `LDAP_REMOVE_CONFIG_AFTER_SETUP=false`. All containers (web, db, openldap, phpmyadmin, phpldapadmin) became healthy. 10 test LDAP users load correctly.
4. **Dependencies**: `ddev composer install --no-interaction` (47 packages) and `ddev npm i` (592 packages) both succeeded.
5. **Database**: `ddev importDump` loaded `dump/db.sql`; 9 tables present.
6. **Config**: `cp config/web.config.local.php.example config/web.config.local.php`. The example's LDAP block was stale (host `ldap`, port `10389`, base `dc=planetexpress,dc=com`), so I aligned the local config to the LDAP service actually defined in `.ddev/docker-compose.ldap.yaml` (`host=openldap`, `port=389`, `dn=cn=admin,dc=example,dc=org`, `baseDn=dc=example,dc=org`).
